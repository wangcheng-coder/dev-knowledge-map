# Java 并发

并发的两个演示都是真实跑出来的：[LostUpdate.txt](../demos/transcripts/LostUpdate.txt) 和 [ThreadPoolReject.txt](../demos/transcripts/ThreadPoolReject.txt)。可见性规则放在这两次结果前面，因为丢失更新和“看不见写入”是两种不同的失败。

## happens-before 规定的是哪一次写入能被看见

Java 内存模型不保证“源码在上面的赋值，另一个线程马上能读到”。它保证的是下面这些关系。关系成立时，前面的写入对后面的读取可见，并且不会被重排到关系的错误一侧：

1. 同一线程里，程序顺序靠前的动作先于靠后的动作。
2. 解锁先于随后对同一把锁的加锁。
3. 对 `volatile` 字段的写先于随后对它的读。
4. `start` 之前的写，对新线程可见。线程里的写，对成功 `join` 回来的线程可见。
5. 这些关系可以传递。

没有关系时，另一个线程可以一直看到旧值。`volatile` 管的是这一个变量的可见性和顺序，不管 `count++` 这种读改写是不是一次完成。

## `++` 为什么会丢

源码 [LostUpdate.java](../demos/src/LostUpdate.java)。8 个线程各自对计数器做 100000 次自增，期望 800000。一次 `volatileCount++` 在字节码里是三步：把值读到栈上，加 1，再写回。两个线程可以都读到 10，都写回 11。`volatile` 让每次读到的是最新值，也让写能被别人看见，但挡不住两个人同时基于同一个旧值写回。

本次运行：

```text
volatile 自增做完
  期望 800000 实际 256127
AtomicInteger 做完
  期望 800000 实际 800000
synchronized 做完
  期望 800000 实际 800000
```

`256127` 只属于这一次。再跑会得到另一个小于 800000 的数。`AtomicInteger.incrementAndGet` 用一条原子的读改写完成加一，`synchronized` 让读改写在同一把锁里，所以这两行每次都是 800000。

锁和原子类解决的是互斥。可见性由进入和退出锁、或者由原子类内部的内存顺序一起带上。

## 线程池接收一个任务时的决定

源码 [ThreadPoolReject.java](../demos/src/ThreadPoolReject.java)。池的参数是：核心线程 1，最大线程 1，队列容量 1，拒绝时打印一句话。第一个任务一进入 `run` 就停在门闩上，故意不结束。

`ThreadPoolExecutor.execute` 的决定顺序是：

1. 工作线程数小于核心线程数，就新建线程执行这个任务。第一个任务把池从 0 变成 1，队列仍是 0。
2. 核心线程已经满了，再来的任务进队列。第二个任务提交时，唯一的线程还停在第一个任务里，队列长度变成 1。
3. 队列也满了，如果线程数还小于最大线程数，再新建线程。这个演示里最大线程数就是 1，走不到这一步。
4. 线程数和队列都到顶，执行拒绝策略。第三个任务打印“拒绝: 唯一线程在忙，队列容量 1 已满”。它的 `run` 没有被调用。

输出：

```text
第 1 个任务占用 worker-1，池大小=1 队列=0
第 2 个任务入队后，池大小=1 队列=1
拒绝: 唯一线程在忙，队列容量 1 已满
第 3 个任务被拒绝后，池大小=1 队列=1
队列中的任务现在才开始执行
```

最后一行是放开门闩之后发生的。队列里的任务并不是被拒绝了，它在唯一的线程有空时才运行。若队列改成无界，第 3 步的“队列满了再扩线程”不会到来，任务会一直堆在内存里，最大线程数没有机会生效。

每个任务都要能结束，或者能响应中断。池关闭时先不再接收，再按策略等待已提交任务或尝试中断。

## 虚拟线程改变的是哪一层调度

JDK 21 的虚拟线程由 JVM 调度到少数平台线程上。阻塞式套接字在阻塞时会让出载体，所以大量“一请求一线程”的阻塞代码可以同时存在。CPU 计算的并行度仍然受核数限制，虚拟线程不会把一段纯计算变成更多并行。

在 `synchronized` 或本地方法里阻塞时，虚拟线程可能一直占着载体。热路径上的阻塞点要单独看它会不会把载体钉住。这段行为随 JDK 版本变化，以所用版本的发行说明为准。

## 容器和线程局部变量

`ConcurrentHashMap` 允许并发读写。桶冲突升级后用同步保护那个桶，计数用分片累加。它的迭代器是弱一致的：不抛 `ConcurrentModificationException`，也不承诺能看见迭代开始之后的每一次插入。

`BlockingQueue` 的容量是生产速度的上限。容量满了，生产者停在队列上，而不是把堆撑满。这和上面的线程池队列是同一件事。

`ThreadLocal` 的值挂在线程上。线程池会复用线程，任务结束时要移除，否则下一个任务读到上一个任务的值，线程还可能把类加载器间接留住。
