# 网络

网络层要解决的是：不可靠的链路上传字节，怎样变成进程可以读写的字节流，并且在拥塞时退让。Java 的 `Socket`、HTTP 客户端和 RPC 都站在这条已经建立的连接上。

## 分层各自负责的事

| 层 | 负责 | 丢了会怎样 |
| --- | --- | --- |
| 链路 | 在一段局域网里把帧送到网卡 MAC | 交换机和网卡处理重传或直接丢帧 |
| 网络 | 按 IP 地址跨网络转发 | 路由器丢包，不负责恢复 |
| 传输 | TCP 提供有序字节流；UDP 保留报文边界 | TCP 重传；UDP 把丢失交给应用 |
| 应用 | HTTP、数据库协议、自定义 RPC | 自己的超时、幂等和重试 |

IP 只承诺尽力转发。TCP 在两端维护序号、确认号和窗口，把丢包变成重传，把乱序变成排序，把发太快变成窗口限制。

## TCP 上和开发直接相关的行为

三次握手交换起始序号并建立双方状态。连接在 `ESTABLISHED` 之后，应用的 `read` / `write` 面对的是字节流，报文边界已经没了。所以应用协议要自己定帧：长度前缀、分隔符或 HTTP 的 `Content-Length`。

拥塞控制假设丢包多半是因为路径太挤，于是减小发送速率。延迟突然升高时，Java 客户端看到的是超时，根因可能在窗口、重传或对端处理不过来。

四次挥手释放双向通道。一边关闭写之后，另一边仍可能继续读完剩余数据。连接池要处理半开连接和对端已经重启的情况。

## 事件驱动

一个线程阻塞在 `read` 上，就只能服务一条连接。`epoll` 让线程向内核登记一批描述符，内核在其中有可读或可写时返回。Netty 的事件循环就是这个模型：少量线程轮询就绪事件，把工作分给流水线里的处理器。

接收方向上，网卡 DMA 把包放进环形缓冲区并中断。内核协议栈处理完，数据进入套接字接收缓冲，`epoll` 才标记可读。发送方向对称。Java 里一次「非阻塞读」只是把已经在接收缓冲里的字节拷进 `ByteBuffer`，没有新数据就立刻返回。

## 名字、TLS、负载

DNS 把名字解析成地址，结果会被缓存。证书校验在 TLS 握手里完成，之后应用看到的才是明文流。负载均衡器可能终结 TCP 或 TLS，再发起到上游的新连接，所以应用看到的对端地址不一定是用户地址。

## 项目

| 项目 | 角色 | 先看什么 | 地址 |
| --- | --- | --- | --- |
| Linux | TCP/IP 与套接字实现 | `net/ipv4`、`net/core` | https://github.com/torvalds/linux |
| nginx | 生产级事件驱动服务器。看连接、缓冲和上游 | `src/core`、`src/event`、`src/http` | https://github.com/nginx/nginx |
| Redis | 单线程事件循环加应用协议，模型小而完整 | `src/ae.c`、`src/networking.c` | https://github.com/redis/redis |
| etcd | 基于 Raft 的协调服务。用来理解「网络分区之后一致性怎么做」 | `server/etcdserver`、`raft` | https://github.com/etcd-io/etcd |
| ZooKeeper | Java 生态里常见的协调服务实现 | `zookeeper-server` | https://github.com/apache/zookeeper |

这一层要能讲清：字节流没有消息边界、超时不等于对端一定没收到、事件循环为什么不能在 I/O 线程里做长时间计算。Java 侧的对应实现在 [I/O 与网络](../java/io-and-network.md)。
