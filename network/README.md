# 网络

这一页按演示里的序号把三次握手和 3 字节数据走完。半包如何在 Java 里拼起来见 [I/O](../java/io-and-network.md)。

## 分层各自负责的字节

| 层 | 这一层加上的信息 | 丢失时谁负责 |
| --- | --- | --- |
| 链路 | 以太网帧头，把帧送到同一局域网的网卡 | 链路自己重传或直接丢帧 |
| 网络 | IP 头，路由器按目的地址转发 | 路由器可以丢包，不负责恢复 |
| 传输 | TCP 头里的序号、确认号和窗口 | TCP 重传、排序、限制发送速率 |
| 应用 | HTTP 或自定义的长度字段 | 应用自己的超时、幂等和重试 |

IP 只承诺尽力转发。应用若自己不规定帧长，TCP 交给它的就是一条没有边界的字节流。

## 序号 1000 和 5000 的握手

源码 [TcpHandshake.java](../demos/src/TcpHandshake.java)，输出 [TcpHandshake.txt](../demos/transcripts/TcpHandshake.txt)。

客户端初始序号选 1000，状态从 CLOSED 进入发送 SYN。服务端在 LISTEN，初始序号选 5000。

1. 客户端发送 `SYN seq=1000`。这个序号占用一个序列号空间，不携带应用字节。客户端进入 `SYN_SENT`。
2. 服务端回复 `SYN+ACK seq=5000 ack=1001`。确认号 1001 表示“1000 这一号我收到了，下一号请从 1001 开始”。服务端进入 `SYN_RECEIVED`。
3. 客户端发送 `ACK seq=1001 ack=5001`。双方进入 `ESTABLISHED`。客户端下一字节的序号是 1001，服务端是 5001。

```text
客户端 CLOSED，服务端 LISTEN
客户端 -> 服务端  SYN seq=1000
服务端 -> 客户端  SYN+ACK seq=5000 ack=1001
客户端 -> 服务端  ACK seq=1001 ack=5001
双方都是 ESTABLISHED。客户端下一字节序号是 1001，服务端是 5001
客户端 -> 服务端  PSH 数据 abc 共 3 字节 seq=1001
服务端 -> 客户端  ACK seq=5001 ack=1004
服务端确认号 1004 = 1001 + 3，表示 1001、1002、1003 都收到了
```

`abc` 三个字节占用序号 1001、1002、1003。服务端确认号写成 1004，意思是这三号之前的都到了，下一号我期待 1004。确认号是“下一字节”，不是“最后一字节”。

字节流没有把 `abc` 的边界保留给下一次 `read`。应用要自己写长度、分隔符或 HTTP 的 `Content-Length`。长度被拆进两次 `read` 时的拼法，由 [FrameDecoder](../demos/src/FrameDecoder.java) 按字节跑过。

## 拥塞、关闭和事件

路径上丢包变多时，TCP 认为路径挤，减小发送窗口。Java 客户端看到的是超时。超时只说明应答没在期限内到，不说明对端一定没收到数据。已经发出去的插入可能已经提交，重试必须能识别重复。

一边调用关闭写之后，另一边仍可以读完剩余数据。连接池要处理这种半关，以及对端进程已经重启、旧连接已经无效的情况。

一个线程若阻塞在一条连接的 `read` 上，就不能看别的连接。`epoll` 让线程登记一批描述符，内核在其中有可读或可写时返回。Netty 的事件循环就是这个模型。就绪之后的处理要短，长时间计算会堵住同一循环上的其他连接。

接收方向上，网卡用 DMA 把帧放进环，再中断。内核协议栈处理完，字节进入套接字接收缓冲，`epoll` 才报告可读。一次非阻塞读只是把已经在接收缓冲里的字节拷出来。

名字先经 DNS 变成地址，结果会被缓存。TLS 握手完成之后，应用才看见明文。负载均衡器可能自己终结 TCP，再发起到上游的新连接，所以应用看到的对端地址不一定是用户的地址。
