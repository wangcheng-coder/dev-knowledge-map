# 语言运行时

运行时把文本源码变成 CPU 能执行的指令，并在进程活着的时候管理代码、内存和线程。C 家族把大量内存责任放在程序员身上。Java 把类型检查、字节码验证、垃圾回收和即时编译放进虚拟机。两套运行时下面是同一套操作系统。

## 编译pipeline

源码先变成词法记号，再变成语法树。语义分析检查类型和名字。之后生成中间表示，在中间表示上做与 CPU 无关的优化，再按目标平台生成汇编和目标文件。

目标文件里是机器码和符号表，地址还没完全定死。链接器把多个目标文件和库合成可执行文件或共享库，做符号解析和重定位。动态链接则把最后一步推迟到进程启动或第一次调用。

LLVM 把「中间表示加多套前后端」做成了可复用的编译基础设施。GCC 是另一套完整的编译器。看它们是为了知道：Java 的 `javac` 停在字节码，真正变成机器码的是 JVM 里的 JIT，不是操作系统。

## 进程装载

加载器按可执行文件头建立地址空间：代码段、已初始化数据、未初始化数据、堆和栈。动态链接器解析共享库。然后跳到入口。Java 程序多了一步：入口是虚拟机本身，虚拟机再装载 `main` 所在的类。

调用约定规定参数放在哪些寄存器、栈谁来清、返回值放哪。JNI 调用本地库时，必须遵守这套约定。本地崩溃往往已经离开了 Java 的异常系统。

## 内存责任的两种做法

手动管理要求每块堆内存有明确的释放点，错误形式是泄漏、重复释放和释放后使用。垃圾回收要求运行时知道哪些引用还活着，从根（栈、寄存器、静态变量）出发标记可达对象，其余回收。

回收换来的是停顿、屏障和额外内存。写 Java 时仍要理解可达性：静态集合、未取消的监听器和类加载器都会把对象留在根上。

## 和 Java 虚拟机的对应

| 通用概念 | 在 Java 里 |
| --- | --- |
| 编译前端 | `javac` 产生 `class` 文件 |
| 中间码 | 字节码 |
| 优化与后端 | C1、C2 即时编译，以及可选的 Graal |
| 装载 | 类加载器把字节码定义成运行时的类 |
| 堆管理 | 垃圾回收器 |
| 本地代码边界 | JNI、Panama 外部函数 |

## 项目

| 项目 | 角色 | 先看什么 | 地址 |
| --- | --- | --- | --- |
| LLVM | 编译基础设施 | `llvm/lib/IR`、`llvm/lib/CodeGen` | https://github.com/llvm/llvm-project |
| GCC | 完整的 C/C++ 编译器实现 | `gcc/` | https://github.com/gcc-mirror/gcc |
| OpenJDK | Java 语言、核心库和 HotSpot 虚拟机 | `src/java.base`、`src/hotspot` | https://github.com/openjdk/jdk |
| Protocol Buffers | 一个具体的「语言中立编码 + 各语言运行时」 | `java/` 与 `src` | https://github.com/protocolbuffers/protobuf |

Protobuf 放在这里，是因为它把「结构如何变成字节，再被另一种语言的运行时读出来」做成了独立项目。网络和应用协议经常是同一类问题。
